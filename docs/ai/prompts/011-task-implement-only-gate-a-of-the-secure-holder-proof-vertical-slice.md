> GATE A SECURITY MODEL
>
> A. SERVER-ISSUED CHALLENGE
>
> Provide a challenge issuer using cryptographically secure Node randomness.
>
> Challenge fields:
>
> credential: bytes32
> resource: bytes32
> nonce: bytes32
> expiresAt: uint64
>
> The challenge store records the exact issued challenge.
>
> Initial logical state:
>
> PENDING
>
> Allow dependency injection of:
>
> * current time
> * random-byte generation
>
> where useful for deterministic tests.
>
> Do not weaken the real/default implementation.
>
> Default nonce generation must use Node cryptographic randomness.
>
> B. CANONICAL TYPED DATA
>
> Build EIP-712 typed data only from SERVER-STORED challenge data.
>
> During verification, do not trust client-supplied values for:
>
> * domain
> * credential
> * resource
> * nonce metadata
> * expiresAt
>
> The proof should eventually require only:
>
> * a challenge identifier / nonce
> * the resulting signature
> * explicit expected credential/resource supplied by the verifier context if
>   needed for binding checks
>
> The verifier reconstructs the canonical challenge internally.
>
> C. CHALLENGE STORE
>
> For Gate A, use an in-memory store only.
>
> No database.
>
> Required logical states:
>
> PENDING
> CONSUMED
>
> Verification must distinguish at minimum:
>
> UNKNOWN_CHALLENGE
> EXPIRED_CHALLENGE
> REPLAYED_CHALLENGE
>
> Expired entries may be cleaned lazily.
>
> The PENDING → CONSUMED transition must be one-way.
>
> D. PRE-HOLDER VALIDATION
>
> Before holder proof can succeed, require:
>
> 1. challenge was issued by this verifier;
> 2. challenge is PENDING;
> 3. challenge is not expired;
> 4. expected credential matches;
> 5. expected resource matches;
> 6. signature is cryptographically valid;
> 7. recovered signer equals the CURRENT ENSv2 credential owner.
>
> The current owner must be evaluated at VERIFICATION time.
>
> Do not permanently bind authorization to the owner present when the challenge
> was issued.
>
> E. REQUIRED ONE-SHOT CONSUMPTION SEMANTICS
>
> This rule is security-critical.
>
> Once ALL of the following have been established:
>
> * challenge is server-issued
> * challenge is PENDING
> * challenge is not expired
> * expected credential matches
> * expected resource matches
> * signature is cryptographically valid
> * recovered signer == CURRENT ENSv2 credential owner
>
> the challenge must transition:
>
> PENDING → CONSUMED
>
> exactly once.
>
> This consumption occurs BEFORE returning the final ENS access-policy result.
>
> The challenge must remain CONSUMED regardless of whether the subsequent ENS
> policy returns ALLOW or DENY.
>
> Examples:
>
> VALID CURRENT HOLDER
>
> * ACTIVE valid ENS access
>
> → consume challenge
> → ALLOW
>
> VALID CURRENT HOLDER
>
> * INACTIVE ENS access
>
> → consume challenge
> → DENY
>
> VALID CURRENT HOLDER
>
> * expired access
>
> → consume challenge
> → DENY
>
> VALID CURRENT HOLDER
>
> * registry/policy condition denies
>
> → consume challenge
> → DENY
>
> RATIONALE
>
> A successful current-holder proof is one-shot.
>
> A legitimate proof presented while access is denied must not remain reusable
> inside its TTL and later become valid merely because ENS access state changes.
>
> Example attack to prevent:
>
> holder presents valid signed challenge
> → access.active=false
> → DENY
>
> attacker captures proof
>
> access changes to active=true before challenge expires
>
> captured proof submitted again
> → MUST NOT become ALLOW
>
> The second submission must return:
>
> REPLAYED_CHALLENGE / DENY
>
> F. DO NOT CONSUME THESE CASES
>
> Do NOT transition to CONSUMED for:
>
> * UNKNOWN_CHALLENGE
> * EXPIRED_CHALLENGE
> * wrong credential
> * wrong resource
> * malformed signature
> * cryptographically invalid signature
> * recovered signer != CURRENT ENSv2 credential owner
>
> Those cases have not successfully established current holder proof.
>
> G. ATOMICITY
>
> Within the Gate A in-memory challenge store, the transition:
>
> PENDING → CONSUMED
>
> must happen exactly once.
>
> After current-holder proof succeeds, no second verifier call may observe the
> challenge as reusable.
>
> Keep the implementation simple, but structure it so this one-shot transition
> is explicit and testable.
>
> H. CURRENT OWNER MATTERS
>
> At verification time:
>
> recover signer from canonical EIP-712 signature
>
> then obtain/use CURRENT ENSv2 credential owner.
>
> Require:
>
> recovered signer == current owner
>
> Therefore:
>
> challenge issued while owner = A
> credential later transferred to B
> A submits old signature
> → DENY
>
> The challenge must NOT be consumed for wrong signer/current-owner mismatch.
>
> I. ENS ACCESS POLICY
>
> Holder proof is necessary but not sufficient.
>
> After valid current-holder proof has been established and the challenge
> consumed, apply the existing ENSv2 authorization policy.
>
> ALLOW requires the existing project's rules, including:
>
> * credential REGISTERED
> * valid/non-zero current owner
> * registry not expired
> * access.active == true
> * access.validUntil > current time
>
> Reuse the existing implementation.
>
> Do not create slightly different holder-proof-specific access semantics.
>
> If the existing project centralizes those rules in a pure helper, call it.
>
> If not, perform the smallest safe refactor necessary to expose/reuse them.
>
> Do not broadly redesign the ENS code.
>

> DENY

>

>
> Attempt verification in context of credential B.
>
> Expected:
>
> DENY
>
> Challenge must NOT be consumed by the wrong-credential attempt.
>
> 10. WRONG SIGNER
>
> Challenge is valid.
>
> Different deterministic EOA signs it.
>
> Current ENS owner is the intended owner.
>
> Expected:
>
> DENY
>
> Challenge remains unconsumed because current-holder proof did not succeed.
>
> 11. CURRENT OWNER CHANGED
>
> Challenge exists.
>
> Owner A signs canonical challenge.
>
> Mock CURRENT ENS owner as B at verification time.
>
> Expected:
>
> DENY
> signer != current owner
>
> Challenge must not be consumed by this wrong-current-owner proof.
>
> 12. UNREGISTERED / INVALID CREDENTIAL POLICY
>
> Correct current holder cryptographic proof succeeds.
>
> Existing ENS policy determines credential is unavailable/unregistered or
> otherwise invalid.
>
> Expected:
>
> DENY
> challenge → CONSUMED
>
